# 功能规格说明书：Agent 调度平台（可配置可扩展智能体编排系统）

**功能分支**: `001-agent-dispatch-platform`
**创建日期**: 2026-04-17
**状态**: 草稿
**输入**: 用户描述："需要一套可配置、可扩展的 Agent 调度平台，统一入口处理用户 query，支持单 Agent（工具调度）与多 Agent（子 Agent 调度）两种流水线；运营人员可配置 MCP 工具、技能、其他 Agent 作为插拔式子系统，并通过商场式界面进行管理。"

## 用户故事与测试场景

<!--
  用户故事按重要程度排序，每个故事独立可测试，代表一个可交付的最小价值切片。

### 用户故事 1 - 终端用户通过单 Agent 获取智能回复（优先级：P1）

终端用户向平台提交问题或指令，平台自动识别意图、选择合适工具，完成任务后将结果整合成自然语言回复返回给用户。整个过程对用户透明。

**为何此优先级**：这是平台最核心的价值交付场景，决定了系统是否可用。无论其他功能是否完备，此场景必须先打通。

**独立测试**：可通过向系统发送一条明确意图的查询（如"今天北京天气如何"），验证系统能否完整走完意图识别→工具调用→结果归纳→输出的完整链路，独立交付价值。

**验收场景**：

1. **Given** 用户提交一个意图清晰的单工具查询，**When** 系统判断仅需调用一个工具，**Then** 系统直接调用该工具，不经过多工具规划步骤，并将工具结果整合成自然语言返回给用户。
2. **Given** 用户提交一个需要多个工具协作的复合查询，**When** 系统判断需要多工具配合，**Then** 系统通过智能规划确定工具调用顺序，依次执行后归纳汇总，输出统一的自然语言回复。
3. **Given** 用户提交的内容触发前置检测规则（如包含违禁词），**When** 系统执行前置检测，**Then** 系统拒绝处理并向用户返回清晰的拒绝说明，不进入工具调用阶段。
4. **Given** 工具调用成功但后置检测发现输出不合规，**When** 系统执行后置检测，**Then** 系统拦截该输出并向用户返回安全提示，不透出违规内容。

### 用户故事 2 - 终端用户通过多 Agent 编排获取智能回复（优先级：P2）

终端用户提交复杂查询，平台智能判断需要哪个或哪些子 Agent 协作处理，编排结果后统一回复用户。用户无需感知底层 Agent 的分工与协作。

**为何此优先级**：多 Agent 编排是平台在复杂场景下的核心能力。单 Agent 模式打通后，此功能是扩展业务覆盖的关键。

**独立测试**：配置两个具备不同能力的子 Agent，向系统提交需要二者协作的查询，验证路由、调度、汇总全链路正常工作。

**验收场景**：

1. **Given** 用户提交的查询经路由判断仅涉及单一子 Agent 且置信度满足配置阈值，**When** 系统执行路由，**Then** 直接将查询转发至该子 Agent，不经过多 Agent 编排步骤，子 Agent 的回复直接作为用户可见内容候选。
2. **Given** 用户提交的查询需要多个子 Agent 协作，**When** 系统执行路由，**Then** 编排模块按规划顺序依次调用各子 Agent，收集所有结果后归纳汇总，生成统一回复。
3. **Given** 任意路由结果，**When** 最终输出前，**Then** 系统 MUST 对候选内容执行后置检测，检测不通过则拦截。
4. **Given** 某子 Agent 响应超时，**When** 编排模块等待超时，**Then** 系统以已有结果继续处理并告知用户部分功能不可用，不整体失败。

---

### 用户故事 3 - 运营人员通过商场式界面配置插拔式子系统（优先级：P2）

运营人员在管理端的"子系统商场"中，浏览可用的 MCP 工具、技能（Skill）和其他 Agent（本平台或第三方），通过安装/启用操作将其纳入平台资源池；也可随时卸载/禁用，无需重启服务。

**为何此优先级**：可配置性是平台"可扩展"核心价值的体现。运营人员能自主扩展能力，减少对研发的依赖。

**独立测试**：在商场中安装一个新 MCP 工具，验证安装后该工具立即出现在可用资源池中，单 Agent 流水线可调用它，卸载后不再可用。

**验收场景**：

1. **Given** 运营人员进入子系统商场，**When** 浏览工具/技能/Agent 列表，**Then** 系统展示所有可用条目，支持按类别（MCP 工具 / 技能 / Agent）和关键词筛选，每个条目显示名称、描述、来源平台、当前启用状态。
2. **Given** 运营人员点击"安装/启用"某一子系统，**When** 操作确认，**Then** 该子系统立即进入已启用状态，运行时通过订阅通知感知变更，无需重启，可被调度流水线使用。
3. **Given** 运营人员点击"卸载/禁用"已启用的子系统，**When** 操作确认，**Then** 该子系统从可用资源池移除，运行时通过订阅通知感知变更，后续调度不再使用该子系统。
4. **Given** 运营人员需要注册一个第三方平台的 Agent，**When** 填写接入信息（名称、接入地址、描述等），**Then** 系统验证连通性后将其加入商场，后续可被安装启用。

---

### 用户故事 4 - 配置变更实时生效，运行时与管理端解耦（优先级：P3）

运营人员在管理端的任何配置变更（工具启用/禁用、检测规则调整、路由阈值修改等），通过订阅通知机制实时推送至运行时，运行时无需重启即可感知并应用最新配置。

**为何此优先级**：解耦设计是平台未来分离部署的基础。P1/P2 场景可先在耦合模式下运行，但此能力是生产可用性和弹性扩展的保障。

**独立测试**：在管理端修改某工具的启用状态，验证运行时在规定时间内（如 5 秒内）感知变更，后续查询行为符合新配置，期间无中断。

**验收场景**：

1. **Given** 运营人员在管理端完成任意配置变更，**When** 变更保存，**Then** 运行时在 10 秒内收到变更通知并应用新配置，不需要重启服务。
2. **Given** 运行时与管理端处于解耦状态，**When** 管理端暂时不可访问，**Then** 运行时使用最后一次成功同步的配置继续服务，不因管理端不可用而中断。
3. **Given** 运行时重启，**When** 启动完成，**Then** 运行时从配置源拉取最新完整配置，并订阅后续变更通知，恢复正常服务。

### 边界情况

- 用户查询为空或仅含空白字符时，系统如何响应？
- 所有已启用工具均不匹配用户意图时，系统如何处理？
- 子 Agent 返回的内容格式不符合预期时，编排模块如何降级？
- 运营人员同时对同一子系统执行冲突操作（如两个操作员同时安装/卸载）时，系统如何保证一致性？
- 第三方 Agent 接入信息变更（如地址迁移）后，存量配置如何更新？

## 功能需求

### 功能性需求

- **FR-001**: 系统 MUST 提供统一的查询入口，接受终端用户的自然语言输入。
- **FR-002**: 系统 MUST 对用户查询执行意图识别和实体提取，并将结构化结果传递至后续流水线步骤。
- **FR-003**: 系统 MUST 在处理查询前执行可配置的前置检测，检测不通过时拒绝处理并返回明确说明。
- **FR-004**: 系统 MUST 在输出结果前执行可配置的后置检测，检测不通过时拦截输出并返回安全提示。
- **FR-005**: 单 Agent 模式下，系统 MUST 判断本次查询所需工具数量，为单工具时直接调用，为多工具时通过智能规划依次调度。
- **FR-006**: 单 Agent 模式的多工具路径下，系统 MUST 对所有工具返回结果进行归纳汇总，生成面向用户的自然语言回复。
- **FR-007**: 多 Agent 模式下，系统 MUST 通过智能路由判断本次查询应路由至哪个或哪些子 Agent。
- **FR-008**: 多 Agent 模式下，路由至单一子 Agent 且置信度满足配置阈值时，系统 MUST 直接转发，子 Agent 回复作为用户可见候选。
- **FR-009**: 多 Agent 模式下，路由至多个子 Agent 时，系统 MUST 通过编排模块以规划方式依次调用，并归纳汇总结果。
- **FR-010**: 系统 MUST 支持流式与非流式两种输出模式，由调用方或配置决定。
- **FR-011**: 运营人员 MUST 能够通过管理界面浏览、搜索、筛选所有可用子系统（MCP 工具 / 技能 / Agent）。
- **FR-012**: 运营人员 MUST 能够将任意子系统安装/启用至运行时资源池，操作后立即生效，无需重启。
- **FR-013**: 运营人员 MUST 能够将已启用的子系统卸载/禁用，操作后立即从调度资源池移除。
- **FR-014**: 运营人员 MUST 能够注册来自第三方平台的 Agent，系统需验证连通性后方可加入可用列表。
- **FR-015**: 配置变更 MUST 通过订阅通知机制推送至运行时，运行时 MUST 在 10 秒内应用变更。
- **FR-016**: 运行时 MUST 与管理端数据存储一定程度解耦，管理端不可用时运行时可使用缓存配置继续服务。
- **FR-017**: 系统 MUST 支持运营人员对已配置的前置/后置检测规则进行增删改查，变更实时生效。

### 关键数据实体

- **Agent**：智能体，可为单 Agent（含工具列表）或子 Agent（被编排 Agent）；属性：名称、描述、类型（单/子/编排）、来源平台、启用状态、接入配置。
- **Tool**：可调用工具，含 MCP 工具和内置工具；属性：名称、描述、接入协议、输入/输出描述、启用状态。
- **Skill**：技能，封装特定能力的执行单元；属性：名称、描述、触发条件、依赖工具列表、启用状态。
- **Pipeline**：调度流水线配置；属性：类型（单 Agent / 多 Agent）、关联 Agent、检测规则集、路由阈值配置。
- **DetectionRule**：前置或后置检测规则；属性：阶段（前置/后置）、规则类型、规则内容、启用状态。
- **RouteResult**：路由决策结果；属性：目标 Agent 列表、置信度、路由依据。
- **ConfigChangeEvent**：配置变更事件，用于运行时订阅；属性：变更类型、变更对象标识、变更内容摘要、时间戳。
- **MarketplaceItem**：商场条目，对 Tool / Skill / Agent 的商场视图；属性：类型、来源、当前启用状态、安装记录。

## 成功指标

### 可量化结果

- **SC-001**: 终端用户从提交查询到收到回复的端到端时延（P95）在单工具场景下不超过 3 秒，多工具/多 Agent 场景不超过 10 秒。
- **SC-002**: 前置/后置检测覆盖率达到 100%（所有查询路径均经过检测，无绕过路径）。
- **SC-003**: 运营人员完成一次子系统安装/启用操作的全流程时间不超过 2 分钟（从浏览到生效）。
- **SC-004**: 配置变更从管理端保存到运行时感知生效的延迟不超过 10 秒（P99）。
- **SC-005**: 管理端不可用期间，运行时使用缓存配置的服务可用率不低于 99%。
- **SC-006**: 运营人员首次使用商场式管理界面，无需培训即可完成子系统的安装、配置和卸载操作（任务完成率 ≥ 90%）。
- **SC-007**: 平台支持同时接入不少于 50 个子系统（工具 + 技能 + Agent 总计），调度决策时延不因数量增加而线性增长。

## 假设

- 终端用户已完成身份认证，平台无需在本功能范围内实现登录注册。
- 运营人员拥有统一的管理权限，无需区分角色级别的细粒度权限控制（V1 阶段）。
- MCP 工具遵循标准 MCP 协议，平台通过协议适配层接入，无需为每个工具定制。
- 第三方 Agent 通过标准的 HTTP 接口暴露能力，平台通过配置接入地址和认证信息即可集成。
- 单 Agent 模式与多 Agent 模式在同一平台实例中共存，由 Agent 类型配置决定使用哪种流水线。
- 前置/后置检测规则的具体策略（内容安全、敏感词、权限等）由运营人员配置，平台提供规则引擎框架，不内置固定规则。
- V1 阶段商场式管理不含评分、评论、版本管理等高级功能，仅支持浏览、搜索、安装/卸载和基础参数配置。
- 订阅通知机制为内部消息总线，V1 阶段不需要对外暴露事件接口。
